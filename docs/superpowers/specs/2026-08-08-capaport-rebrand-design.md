# CapaPort 全量品牌迁移设计

日期：2026-08-08

状态：已确认

## 1. 目标

将产品品牌和全部技术标识统一为 CapaPort，使产品定位、界面文案、分发产物和项目文档保持一致。项目当前处于 0.1.0 阶段，本次采用断代迁移，不保留旧品牌兼容入口，也不改写 Git 历史。

统一品牌口径：

- 品牌名称：`CapaPort`
- 英文引导语：`One capability. Every agent.`
- 中文引导语：`一种能力，安全抵达每一个 Agent。`
- 产品定义：`跨 Agent 的企业 AI 能力治理与分发平台`

## 2. 命名原则

`CapaPort` 由 Capability 与 Port 组成。Capability 覆盖 Skill、Prompt 和项目上下文，不把产品限制为某一种资产；Port 同时表达能力港口、跨平台移植和软件连接端口。所有新增文案应围绕“组织能力资产”“安全治理”“跨 Agent 分发”和“持续更新”展开，避免再使用“门”“入口”或纯 Agent 网关叙事。

品牌展示统一使用 `CapaPort`；全大写字标可使用 `CAPAPORT`。命令、包名、目录、域名和机器标识统一使用小写 `capaport`；环境变量使用大写前缀 `CAPAPORT_`。

## 3. 迁移范围

### 3.1 产品界面与用户文案

更新 Web、Desktop、CLI 中的产品名称、登录引导、品牌组件、页脚、设备名称、错误提示、诊断文件名、能力标识和无障碍标签。首页和登录入口使用统一引导语，其他页面按上下文使用简短产品定义，不机械重复口号。

品牌相关 CSS 类名、测试选择器和 E2E 注入变量同步改名，避免源码内部继续保留旧品牌语义。

### 3.2 JavaScript 与 TypeScript 包

将 workspace 根包、应用包、共享包和适配器包的 npm scope 统一为 `@capaport/*`，同步更新全部 import、依赖声明、构建配置、测试配置和锁文件。

CLI 命令统一为 `capaport`，构建产物统一为 `capaport-cli.mjs`，帮助文本、安装示例、错误提示和发布脚本同步更新，不提供兼容别名。

### 3.3 能力包协议

能力清单统一为 `capaport.yaml`，schema 统一为 `capaport.io/v1alpha1`。解析器、生成器、fixture、示例、测试和错误提示必须一起迁移。

本次不兼容旧清单名称或旧 schema。已有旧格式能力包需要重新生成，不增加自动迁移分支。

### 3.4 本地状态与系统集成

将本地缓存键、应用数据目录、安装锁目录、临时文件、系统凭据服务名、诊断文件、浏览器存储键和测试注入变量迁移到 `capaport` 命名空间。旧本地状态不自动读取或迁移。

环境变量统一使用 `CAPAPORT_*` 前缀。Docker 镜像、容器、网络、卷、对象桶默认值、服务标识、日志字段、邮件发送方和部署示例同步更新，不保留旧环境变量回退。

### 3.5 文档与文件名

更新 README、PRD、用户指南、管理员指南、验收报告、架构规格、实施计划、发布说明和脚本注释。包含旧品牌的当前项目文件名改为 CapaPort，包括 PRD、设计文档和计划文档中的品牌段。

Git 历史、既有提交消息和不可变的外部审计记录不改写。仓库物理父目录不属于产品契约，本次不移动当前工作区父目录，避免破坏工作区绑定；仓库内容中不保留旧名称。

## 4. 实施顺序

1. 建立全仓旧品牌基线，按包标识、协议、运行时状态、部署和展示文案分类。
2. 迁移 workspace 包名和 import，使依赖图恢复可解析。
3. 迁移能力包协议、CLI、运行时状态和系统集成标识。
4. 更新 Web、Desktop 和 CLI 品牌界面及引导文案。
5. 更新文档、示例、脚本、文件名和生成产物名称。
6. 重新生成 pnpm 锁文件，执行格式化和分层测试。
7. 执行全仓残留扫描与完整发布验证。

实施必须保留工作区中迁移前已经存在的未提交功能改动。若品牌替换与这些改动落在同一文件，应在当前内容上迁移，不回退文件或选择旧版本覆盖。

## 5. 验证标准

迁移完成需同时满足：

- 排除 `.git`、依赖目录、构建产物和不可变历史后，旧品牌残留检测结果必须为零。
- 所有 workspace 包可解析，pnpm 锁文件与 package manifests 一致。
- 能力包解析、生成、安装、发布和更新测试全部使用 `capaport.yaml` 与 `capaport.io/v1alpha1`。
- Web、Desktop、CLI 的品牌展示、引导语、帮助文本和测试预期一致。
- 单元测试、类型检查、lint、构建、安全门禁及项目完整发布校验通过。
- 最终 diff 不丢失迁移前已有的未提交功能修改，也不包含与品牌迁移无关的重构。

## 6. 风险与处理

- **包名批量变化导致依赖失配**：先统一 manifests 与 imports，再重新生成锁文件并运行 workspace 构建。
- **协议断代导致旧能力包不可用**：这是本次明确接受的行为，通过文档和错误提示只描述新格式。
- **缓存或凭据无法沿用**：这是本次明确接受的行为，用户需要重新登录和重新建立本地索引。
- **机械替换破坏自然语言**：技术标识可批量迁移，用户可见文案逐处复核，确保语义围绕能力治理与分发。
- **覆盖现有未提交工作**：修改前记录 dirty worktree，按文件审阅 diff，只追加品牌迁移所需变化。

## 7. 非目标

- 不新增产品功能、权限模型或数据迁移工具。
- 不改变现有业务流程和架构边界。
- 不注册域名、商标或 npm 组织。
- 不改写 Git 历史。
- 不移动当前本地仓库目录。
